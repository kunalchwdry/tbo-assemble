# Ongoing public route-traffic collection

This is a limited **research archive**, not TBO bookings, hotel demand, fares or an inventory-allocation input. It is separate from the flight-ticket price predictor and the historical StatsForecast experiment. Historical and prospective source inputs are DGCA/Ministry of Civil Aviation passenger counts; historical aggregation comes from [Vonter/india-aviation-traffic](https://github.com/Vonter/india-aviation-traffic) under [ODbL 1.0](https://opendatacommons.org/licenses/odbl/1-0/) and official workbooks under [DGCA's website policy](https://www.dgca.gov.in/digigov-portal/jsp/dgca/footerLink/WebsitePolicy.jsp). Review terms before redistribution or commercial use; capture does not establish reuse rights.

## Collection

The Vercel scheduler is configured to **attempt** collection weekly on Monday during the 05:00 UTC hour; precise execution time is not guaranteed. Vercel may skip a job, a source may fail or a function may time out. There is no automatic alert or guaranteed retry. The status card reports the latest recorded attempt across all six routes and the latest valid snapshot for the chosen route; an absent or stale run is not a success. A partial or failed attempt can be retried by an authorized operator; the next scheduled attempt occurs in the following week. The route requires the existing Vercel `CRON_SECRET` bearer token, never shown in the browser. No new paid service is required; Vercel Hobby and Supabase limits still apply and free availability is not guaranteed. Vercel Hobby is for personal, non-commercial projects; check provider terms and quotas before any commercial use.

Only one server-fetched snapshot per route per UTC week is retained, and the archive stops at **104 per route**. No automatic deletions. The database tables have RLS enabled with direct access denied to anonymous and authenticated Supabase roles; the server exposes only bounded route status and aggregate results. DB administrators can still alter data: hashes detect unintentional changes, not a privileged attacker, and this is not an immutable audit log. An SHA-256 of normalized rows including provenance is checked before use, alongside the recorded upstream source-manifest hash. Snapshot data contains public route totals and source references, not user data. Only successfully validated source results are saved; per-route failures do not prevent other routes from completing. Server and database clocks must agree within five minutes, but their agreement cannot establish true time.

**Clock warning:** during implementation, the source/API/database clocks returned 15 November 2026, while the session date was 13 November 2026. The clocks' absolute accuracy is unresolved. Recorded times are infrastructure claims, not independently certified evidence. Do not claim independent prospective validation until trusted chronology is verified. The UI also warns when a capture is in the future relative to the device clock.

## What can be evaluated

For each captured route, the current `india-traffic-v4` method is frozen only if its existing freshness and eligibility gate allows a **future** target. Both last-observed and last-year baselines are recorded for the same target. If sources are stale, the snapshot is retained but no forecast is invented. Once a later saved snapshot after the target month contains one valid target observation, the first recorded forecast for that target is scored on that first available observation, without substituting later revisions. Aggregate MAE uses the same targets for all three methods. If the source later revises the value, the first available value may be wrong; DB administrators can still alter the archive and timing is not independently certified. Samples will initially be empty or small, and no accuracy, procurement or profit claim is warranted.

This server-side check **does not itself fit StatsForecast**. A separate [scheduled StatsForecast research experiment](/research/statsforecast-forward.md) is configured to freeze eligible predictions and score later captured outcomes. Neither clock chronology nor first production execution is independently verified; never backdate predictions or infer historical availability from revised data.
