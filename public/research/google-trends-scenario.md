# Google Trends travel interest via SerpApi

The Market context page can request a fixed travel query from the existing SerpApi key. Queries are restricted to a small allowlist; the request uses India, `today 3-m`, daily timeseries and UTC. Results contain a relative Google Trends interest index from 0 to 100, not absolute search counts, bookings, look-to-book, prices or supplier availability. Google Trends can contain non-travel searches, uses sampled/normalized values, can revise values and has country and term coverage limitations. Values from separate requests are not directly comparable. Check provider rights before operational use.

No request is automatic. The server stores a successful parsed result in the Next.js cache for 24 hours; cache invalidation, concurrent misses and revalidation can cause extra calls. Before each upstream call the server atomically reserves the same shared database budget as the existing flight-price search: at most 8 attempts per UTC day and 180 over 30 days in this app. Failures and timeouts count; unavailable database fails closed. Other apps and uses of the key aren't counted, and this limit cannot guarantee your account will never exceed provider plan limits or be billed; verify the provider account. The key remains server-side. Raw provider errors are not returned.

A valid daily series requires at least 14 complete consecutive days; duplicate, malformed, missing, partial or insufficient observations do not produce a usable response. Only completed days are included. To compare a scenario, the matching item must have the same destination and type (and, for the supported flights, origin text), the review date must be today UTC, the newest completed day must be at most three days old, fetched data must be at most 26 hours old, and the previous seven-day index sum must be at least 35. These checks do not verify that the product, route or travel period really matches the query.

The hypothetical adjustment is `1 + clamp((recent7 / previous7 - 1) * 0.10, -0.10, +0.10)`, multiplied by the selected item's current signal (limited to the planner's allowed range). It is an assumed sensitivity, not a trained coefficient. Only one item is adjusted in a re-optimized comparison using the current budget, risks and remaining inputs. It does not change the main plan, exports, API inputs or saved plans, and it disappears on refresh. The comparison is blocked if the separate Wikipedia attention scenario is enabled. It can be compared with an experimental fitted blend, but their combined effect is not validated. Historical Google Trends values returned today are normalized using the requested window and may be revised; they cannot be treated as a historically available as-of snapshot without archival evidence.

This is an exploratory signal and not a predictive model or purchasing recommendation. To demonstrate added predictive value, obtain representative timestamped booking/search outcomes and archived as-of signals, compare models with and without the signal on chronological holdouts, and test prospectively. No actual stock, quote or order is created.
